# زیرساخت قالب Citynet

## محل کدها

`functions.php` فایل راه‌انداز است. `inc/actions.php` اکشن‌های عمومی راه‌اندازی،
Customizer، ثبت رشته‌های هدر و آماده‌سازی آرشیو دسته را نگه می‌دارد.
`inc/filters.php` فیلترهای عمومی کلاس بدنه و منو را نگه می‌دارد.
هوک‌های امنیت، کش، فونت، asset و ACF در فایل زیرساخت مربوط به خودشان هستند.
کال‌بک‌های هوک‌ها نام‌دارند و با همان نام قابل حذف با `remove_action` یا
`remove_filter` هستند. برای مقادیر ثابت استاندارد، از توابع `__return_*` استفاده می‌شود.

`inc/ajax-callbacks.php` جایگزین فایل سابق ادغام دسته شده و ورودی HTTP جستجو را
اعتبارسنجی می‌کند. منطق قابل استفادهٔ مجدد جستجو در `cn_search_results()` داخل
`inc/search.php` و منطق کوئری دسته در `cn_category_query_args()` داخل
`inc/helpers.php` است. فایل `category.php` در ریشه همچنان قالب آرشیو وردپرس است.
صفحه‌بندی دسته همچنان با GET به URL واقعی آرشیو کار می‌کند.

## محافظت پوشه‌ها

پس از افزودن پوشه و پیش از بسته‌بندی یا انتقال به هاست، از ریشهٔ وردپرس اجرا شود:

```powershell
php wp-content/themes/citynet/tools/protect-directories.php
php wp-content/themes/citynet/tools/protect-directories.php --check
```

فرمان اول پوشه‌های پدر و چایلد را بازگشتی بررسی و فقط فایل‌های مفقود را ایجاد می‌کند.
فرمان دوم فقط بررسی می‌کند و در صورت نبود فایل، exit code برابر ۱ برمی‌گرداند.
فایل موجود بازنویسی نمی‌شود؛ symlinkها دنبال نمی‌شوند. مسیر چایلد دیگری را می‌توان
به‌عنوان آرگومان داد؛ مسیر باید یک قالب مستقیم داخل `wp-content/themes` باشد.
این کار در مرحلهٔ آماده‌سازی انجام می‌شود و هر بازدید سایت باعث اسکن یا نوشتن فایل نمی‌شود.

محتوای محافظ زیرپوشه‌ها:

```php
<?php
// Silence is gold!
```

`index.php` پدر، fallback واقعی وردپرس است. `index.php` ریشهٔ چایلد در درخواست
مستقیم خروجی ندارد و در اجرای وردپرس، fallback پدر را بارگذاری می‌کند؛ بنابراین
آرشیوها و سایر صفحه‌های وابسته به fallback به صفحهٔ خالی تبدیل نمی‌شوند.

## ثبت رویدادها

`inc/log.php` از تابع `citynet_log( $message, $file_name, $data )` استفاده می‌کند.
اگر افزونه یا چایلد این تابع را قبلاً تعریف کرده باشد، تعریف موجود حفظ می‌شود.
نسخهٔ همراه قالب همان سربرگ `Local time` و آرشیو روزانه را دارد؛ با WP-Parsidate
تاریخ جلالی و بدون آن تاریخ میلادی ثبت می‌شود. ساعت، `Asia/Tehran` است.

محل پیش‌فرض بیرون از document root وردپرس است:

```text
app/citynet-log/<Jalali-date>/activity.log
```

برای این نصب، مسیر `C:/Users/123/Local Sites/base1405/app/citynet-log` است.
اگر هاست اجازهٔ نوشتن در این مسیر ندارد، یک مسیر خصوصی و قابل‌نوشتن در
`wp-config.php` با `CN_LOG_DIR` مشخص شود. این ثابت مخصوص نسخهٔ همراه قالب است؛
تعریف قبلی تابع لاگ ممکن است تنظیمات مستقل خود را داشته باشد.

رویدادهای خودکار:

- ورود، ورود ناموفق، خروج، ثبت‌نام، ویرایش و حذف کاربر، تغییر نقش و بازنشانی رمز؛
- ایجاد، ویرایش، انتقال به زباله‌دان، بازیابی و حذف محتوا، شامل post typeهای سفارشی و رسانه‌ها؛
- ارسال دیدگاه، ویرایش، تغییر وضعیت و حذف آن؛
- ارسال موفق فرم فرانت‌اند ACF و ذخیرهٔ تنظیمات ACF؛
- تکمیل جستجوی زنده، فقط با زبان و تعداد نتایج.

revision، autosave و auto-draft ثبت نمی‌شوند. لاگ شامل شناسه و وضعیت است؛ نام
ورود، رمز، کوکی، nonce، توکن، متن جستجو و بدنهٔ کامل فرم ثبت نمی‌شوند.
نوشتن فایل با قفل append انجام می‌شود و شکست ثبت لاگ، ذخیره یا ورود را متوقف نمی‌کند.

برای فرم‌های سفارشی، پس از اعتبارسنجی و ذخیرهٔ موفق در handler خود فرم:

```php
do_action( 'cn/form/submitted', 'contact', array( 'object_id' => $entry_id ) );
do_action( 'cn/interaction', 'reservation.confirmed', array( 'object_id' => $reservation_id ) );
```

این هوک‌ها سمت سرور هستند و endpoint عمومی برای ثبت رویداد ندارند. فرم یا
احراز هویت مستقلی که در سرویس خارجی انجام می‌شود باید در handler همان سرویس
به این اتصال متصل شود؛ اجرای هر POST به‌تنهایی نشانهٔ موفقیت فرم نیست.

## زبان و ترجمه

`CN_DEFAULT_LANG` در `wp-config.php` برابر `fa` است. `cn_get_default_language()`
ابتدا همین ثابت را می‌خواند و در نبود ثابت، `fa` را برمی‌گرداند.
`cn_is_persian_language()` فقط خروجی `cn_get_current_language()` را با `fa` مقایسه می‌کند.
همهٔ متن‌های جستجو از `cn_translate()` و کاتالوگ‌های والد/چایلد خوانده می‌شوند.
رشته‌ها هنگام خروجی HTML و attribute با escape متناسب استفاده می‌شوند؛ JSON
جستجو و دادهٔ JavaScript با APIهای JSON/localize وردپرس ارسال می‌شوند.

## خطای جدول کاربران روی هاست

خطای پیوست می‌گوید جدول کاربران در دیتابیس هاست وجود ندارد. فراخوانی WPML در
stack trace، از طریق `wp_reset_query()` و `get_userdata()` این وضعیت را آشکار
کرده است. حذف فراخوانی WPML یا پنهان‌کردن خطا، جدول مفقود را ترمیم نمی‌کند.

برای بررسی فقط‌خواندنی روی هر نصب:

```powershell
php wp-content/themes/citynet/tools/check-user-tables.php
```

این ابزار جدول‌های مؤثر `$wpdb->users` و `$wpdb->usermeta` را بررسی می‌کند و
هیچ تغییری در schema نمی‌دهد. روی نسخهٔ محلی هر دو جدول موجود بودند. برای هاست
باید import کامل دیتابیس، دیتابیس انتخاب‌شده، `$table_prefix` و ثابت‌های احتمالی
`CUSTOM_USER_TABLE` و `CUSTOM_USER_META_TABLE` با نام واقعی جدول‌ها تطبیق داده شوند.
دیتابیس هاست در این workspace در دسترس نیست و تعمیر آن در این تغییرات انجام نشده است.

## بررسی‌های توسعه

```powershell
php wp-content/themes/citynet/tools/test-infrastructure.php
php wp-content/themes/citynet/tools/protect-directories.php --check
php wp-content/themes/citynet/tools/compile-translations.php
```

تست مستقل بدون بارگذاری دیتابیس، ورودی AJAX، nonce، زبان، کش، ترجمه، کوئری دسته
و رویدادها/حذف اطلاعات حساس را بررسی می‌کند. تست HTTP محلی، خروجی واقعی صفحات،
جستجوی مهمان، حفاظت کاربران REST و index پوشه‌ها را نیز پوشش می‌دهد.
