آخرین تطبیق با کد و تنظیمات نصب محلی: **۱۴ اکتبر ۲۰۲۶ / ۲۰۲۶-۱۰-۱۴**.
این سند برای توسعه‌دهنده‌ای است که بعداً پروژه را باز می‌کند. خواسته‌های گفتگو،

شرح پیام‌ها جایگزین بررسی کد نیست؛ رفتار مستندشده با فایل‌های فعلی تطبیق داده شده است.

## پروژه از کجا ادامه پیدا می‌کند؟

ریشهٔ وردپرس `C:\Users\123\Local Sites\woo-theme-1405\app\public` و آدرس محلی
`http://woo-theme-1405.local` است. قالب فعال **چایلد VoiceWeb** است؛ والد باید نصب باشد.
ورود و پرداخت دو افزونهٔ مستقل‌اند. ظاهر و اتصال‌های ووکامرس داخل قالب والد پیاده شده‌اند.
تغییر قالب به‌تنهایی کاربران، دفترچه و آرشیو رسیدها را پاک نمی‌کند.

| لایه | مسیر از ریشهٔ وردپرس | مسئولیت |
|---|---|---|
| قالب والد | `wp-content/themes/voiceweb/` | زیرساخت، تمپلیت، فروشگاه، حساب، آدرس، فیلتر و هدر |
| قالب فعال چایلد | `wp-content/themes/voiceweb-child/` | شخصی‌سازی سایت و overrideها |
| ورود | `wp-content/plugins/voiceweb-auth/` | OTP، ثبت‌نام، رمز ثابت، پیامک و نوار موبایل |
| پرداخت | `wp-content/plugins/voiceweb-payments/` | بله‌پی، کارت‌به‌کارت، رسید و تأیید پرداخت |
| مستندات مرکزی | `wp-content/themes/voiceweb/Doc/` | تحویل و راهنماهای معماری/عملیات |

در زمان بررسی، Auth `1.1.0` و Payments `1.0.0` فعال‌اند. پیامک انتخاب‌شده مهر افراز است.
کاوه‌نگار هنوز تنظیم نشده؛ بله غیرفعال و بدون اعتبارنامه است. کارت‌به‌کارت اکنون فعال
و دارای یک کارت مقصد است. این‌ها وضعیت **این نصب در این تاریخ** هستند، نه تنظیمات
پیش‌فرض نصب افزونه. شماره‌ها، رمزها، کلید سفارش و توکن‌ها عمداً در مستندات درج نشده‌اند.

## قراردادهای قطعی که باید حفظ شوند

1. برند قالب `VoiceWeb / ویس وب` است. سیستم قدیمی Citynet و چارچوب Tour مبنای پروژه نیستند.
2. توسعهٔ ووکامرس در فایل‌های معمول `inc/woocommerce/`، `template-parts/woocommerce/`،
   Sass و JS قالب باشد؛ کاربر صریحاً استفاده از `inc/Modules` را رد کرده است.
3. Auth قابل استفاده در سایت دیگر و واردکردن با یک خط PHP است؛ ظاهر فروشگاه را به آن منتقل نکن.
4. ابتدا تأیید موبایل، سپس نام کاربری و رمز برای مشتری جدید؛ ورود بعدی به‌صورت پیش‌فرض OTP است.
5. موبایل تأییدشدهٔ حساب با موبایل گیرندهٔ سفارش دو دادهٔ جدا هستند.
6. آدرس سفارش قبلی snapshot است؛ دفترچهٔ فعلی نباید بی‌اجازه آن را عوض کند.
7. منوی حساب موبایل عمودی است و اسلاید افقی ندارد؛ نوار پایین شامل خانه، فروشگاه، سبد و حساب است.
8. پرداخت فقط با تأیید معتبر سمت سرور یا بررسی مدیر انجام می‌شود؛ بازگشت به سایت/تصویر رسید کافی نیست.
9. از مسیرهای بومی ووکامرس برای سفارش، موجودی، مالیات، علاقه‌مندی و پرداخت استفاده شود.
10. سورس استایل Sass است؛ خروجی CSS متناظر و PO/MO ترجمه باید همراه تغییر به‌روز شوند.

## ۱. حذف وابستگی قدیمی و تغییر برند

در آغاز گفتگو مسیرهای قالب `citynet`، `front-page.php`، `header.php`، افزونهٔ اصلی Citynet
و `inc/acf-field-groups.php` مطرح شدند. خواستهٔ نهایی حذف ارتباط‌های سیستم قدیمی و
تغییر سراسری نام قالب به VoiceWeb بود. در ساختار فعلی قالب‌ها `voiceweb` و
`voiceweb-child` هستند؛ افزونهٔ اصلی Citynet و لودر Tour در مسیرهای اجرایی قالب حضور ندارند.

پیشوندهای API مانند `cn_*`، کلاس‌های CSS مانند `cn-site-header` و کلیدهای ACF مثل
`field_cn_*` و `group_cn_*` برای سازگاری داده و توسعه باقی مانده‌اند. آن‌ها نام نمایشی
برند نیستند. جایگزینی کور این کلیدها می‌تواند تنظیمات، فیلدهای ذخیره‌شده و hookهای چایلد
را قطع کند؛ تغییرشان migration مستقل می‌خواهد.

بستهٔ فعال `wp-content/plugins/getConfCitynet-main/core.php` نام نمایشی **WP Options Sync** دارد و یک افزونهٔ
ثالث نصب‌شدهٔ کاربر است؛ همان افزونهٔ اصلی حذف‌شده نیست. صرف نام پوشه، مجوز حذف یا
تغییر اعتبارنامهٔ آن نیست. نام `tour` در تست router/search و مثال مستندات فقط دادهٔ فرضی
post type است؛ وجود این نام به معنی سیستم تور فعال نیست.

تعریف ACF سه گروه Local PHP دارد: صفحهٔ بلاگ، هدر/فوتر و آیکون دسته. پوشهٔ تاریخی
`Doc/acf-import` وجود ندارد. منبع schema در `inc/acf-field-groups.php` والد است.
[جزئیات ACF](./ACF-CODE-FIRST.fa.md)

## ۲. افزونهٔ ورود و ثبت‌نام

خواسته: پلاگین مستقل، ورود سریع پیامکی، تکمیل خودکار کد و رمز، ثبت‌نام با نام کاربری/رمز
پس از OTP، هدر دسکتاپ و تجربهٔ مناسب موبایل. نتیجه در `voiceweb-auth` پیاده شده است.

| مرحله | رفتار فعلی |
|---|---|
| ورود اولیه | شمارهٔ ایرانی دریافت و رقم فارسی/عربی و پیش‌شمارهٔ ایران استاندارد می‌شود |
| ارسال | کد شش‌رقمی، زمان اعتبار، فاصلهٔ ارسال دوباره و خطای خوانا |
| تأیید حساب جدید | OTP معتبر اجازهٔ ده‌دقیقه‌ای ثبت‌نام در همان مرورگر می‌دهد |
| ساخت حساب | نام کاربری و رمز واقعی وردپرس؛ نقش customer با Woo یا subscriber بدون آن |
| ورود حساب موجود | موبایل تأییدشده و کد صحیح مستقیماً وارد می‌شوند |
| ورود با رمز | نام کاربری، ایمیل واقعی یا موبایل تأییدشده همراه رمز ثابت |
| حساب قدیمی | تأیید موبایل + رمز صحیح حساب قدیمی برای اتصال؛ billing_phone به‌تنهایی کافی نیست |
| Autofill | one-time-code/WebOTP، username/current-password/new-password؛ ورود دستی هم موجود است |

ایمیل ساختگی تولید نمی‌شود. حساب بدون ایمیل می‌تواند وارد شود؛ ایمیل سفارش‌ها زمانی
قابل ارسال است که مشتری ایمیل واقعی ثبت کند. OTP پیش‌فرض برای customer/subscriber است؛
حساب مدیریتی از ورود با رمز استفاده می‌کند. نگهداری OTP، CSRF، rate limit و قفل هم‌زمانی
در افزونه است و با وابستگی به ACF/Bootstrap/jQuery انجام نشده است.

یک ارسال واقعی مهر افراز و جریان ثبت‌نام، در مرحلهٔ توسعه با شمارهٔ مجاز کاربر آزمایش شد.
این اجازه به معنی ارسال آزاد پیامک در نگهداری آینده نیست. آزمون‌های معمول از سرویس
شبیه‌سازی‌شده استفاده می‌کنند. [ساختار و قرارداد کامل](./AUTH.fa.md)

## ۳. افزودن کاوه‌نگار

خواستهٔ بعدی پشتیبانی از فایل نمونهٔ Kavenegar و امکان انتخاب سرویس بود. نسخهٔ فعلی دو
گزینهٔ مهر افراز و کاوه‌نگار Lookup دارد. انتخاب در **تنظیمات ← ورود ویس وب** انجام می‌شود؛
تنظیمات هر دو هنگام جابه‌جایی حفظ می‌شوند، ولی فقط سرویس منتخب ارسال می‌کند.

کاوه‌نگار از `verify/lookup`، الگوی تأییدشده و `token` خودکار OTP استفاده می‌کند؛ tokenهای
ثابت اختیاری ۲، ۳، ۱۰ و ۲۰ نیز پشتیبانی می‌شوند. WebOTP در کاوه‌نگار به متن خود الگو وابسته
است. کلید و رمز در سورس/فرانت‌اند نیستند. fallback خودکار به سرویس دیگر وجود ندارد تا
خطای ارسال موجب دو پیامک و دو هزینه نشود. ارسال واقعی کاوه‌نگار هنوز انجام نشده است.

## ۴. طراحی ووکامرس و دفترچهٔ چندآدرسی

خواسته: سایدبار زیبا با hook جدا، نام «آدرس‌ها»، چند آدرس، ایران پیش‌فرض، انتخاب هنگام خرید،
ثبت آدرس در مودال و ظاهر مرتب و واکنش‌گرا. کاربر محل پیاده‌سازی را از افزونه به قالب تغییر داد
و چارچوب Modules را رد کرد. نتیجهٔ نهایی در فایل‌های سادهٔ قالب والد قرار دارد.

پوستهٔ فروشگاه، محصول، سبد، checkout، حساب، جزئیات سفارش و پرداخت سفارش با Sass طراحی شده‌اند.
تمپلیت‌های بومی و بلوک‌های فعلی ووکامرس حفظ شده‌اند؛ این کار به معنی بازنویسی تمام ایمیل‌ها،
صفحات مدیریت یا همهٔ تمپلیت‌های ممکن ووکامرس نیست. استایل حساب hook جدا
`voiceweb/woocommerce/account-styles` دارد.

دفترچه تا ۲۰ آدرس دارد. ثبت/ویرایش در مودال، حذف، پیش‌فرض، اعتبارسنجی موبایل/کدپستی،
revision و مالکیت خصوصی موجودند. کشور همیشه `IR` است و از کاربر دوباره سؤال نمی‌شود.
آدرس بومی billing/shipping یک بار و بدون تکرار وارد دفترچه می‌شود. استان/شهر با دادهٔ
ووکامرس فارسی پیشنهاد می‌شوند؛ بدون آن شهر دستی قابل ورود است.

در checkout جدید، آدرس انتخابی به customer و محاسبات بومی Woo منتقل می‌شود. آدرس جدید
بعد از ذخیره برای خرید جاری انتخاب می‌شود؛ انتخاب خرید با پیش‌فرض دفترچه مستقل است.
پیش از ثبت سفارش، مالک و revision دوباره بررسی می‌شوند؛ ایمیل واردشده حفظ می‌شود.
[ذخیره، API و اتصال بلوکی/کلاسیک](./WOOCOMMERCE.fa.md)

## ۵. اصلاح شهرها و آدرس پرداخت سفارش موجود

دو اشکال مشخص در گفتگو گزارش شد:

- هشدار نبودن کتابخانهٔ jQuery شهرهای ایران: وابستگی `pw-iran-cities` به asset مربوط
  اضافه و ترتیب بومی jQuery برای کد inline افزونه حفظ شد.
- اطلاعات آدرس در درخواست می‌آمد، ولی صفحهٔ `/checkout/order-pay/{id}` روی «بارگذاری»
  می‌ماند: پنل خرید جدید در HTML این مسیر تزریق می‌شد، درحالی‌که assets خرید جدید نباید
  آنجا لود شوند. کاربر روشن کرد که می‌خواهد **آدرس ثبت‌شدهٔ همان سفارش** دیده شود.

حالا `voiceweb_wc_is_new_checkout()` مسیر order-pay را جدا می‌کند. hook
`before_woocommerce_pay_form`، پس از تأیید دسترسی و کلید سفارش توسط Woo، فایل
`template-parts/woocommerce/order-pay-address.php` را اجرا می‌کند. آدرس سفارش مستقیم
از PHP نمایش داده می‌شود؛ نیازی به REST دفترچه، مودال یا JS لود آدرس نیست.
این اصلاح سفارش واقعی گزارش‌شده را بازنویسی نمی‌کند. تست کلید نامعتبر نیز مانع نمایش
اطلاعات سفارش می‌شود.

## ۶. سایدبار، نوار موبایل و هدر دسکتاپ

کاربر خواست منوی حساب در موبایل اسلاید افقی نخورد و گزینه‌ها زیر هم باشند؛ سایدبار
فعلی عمودی و واکنش‌گراست. نوار ثابت پایین ابتدا خانه/فروشگاه/حساب بود، سپس سبد افزوده شد.
قالب لینک سبد را با `voiceweb_auth/mobile_navigation_items` به نوار مستقل Auth اضافه می‌کند.

در دسکتاپ، کلیک حساب کاربر واردشده ابتدا منوی نام، موبایل، مشاهدهٔ پروفایل، سفارش‌ها،
علاقه‌مندی‌ها و خروج را باز می‌کند. مهمان همچنان فرم Auth را می‌بیند. Escape، کلیک بیرون،
حرکت با کلیدها و خروج nonceدار پشتیبانی می‌شوند. سبد خرید دسکتاپ نیز به هدر اضافه شد.

شمارندهٔ سبد در هر دو محل زنده است؛ سبد خالی عدد ندارد و مقدار زیاد `99+` نمایش داده می‌شود.
دادهٔ بومی بلوک `itemsCount` با پاسخ REST `items_count` تفاوت دارد؛ JS مشترک هر دو را
پشتیبانی می‌کند. درخواست‌های هم‌زمان تجمیع می‌شوند و پاسخ قدیمی شمارندهٔ جدید را عقب نمی‌برد.

## ۷. علاقه‌مندی‌ها

کاربر افزودن واقعی علاقه‌مندی‌ها را تأیید کرد. از ویژگی بومی `product_wishlist` ووکامرس
استفاده شده؛ صفحهٔ `/my-account/wishlist/` و ذخیرهٔ خصوصی متعلق به Woo هستند. یک adapter
در قالب، محصول کلاسیک ساده یا variation انتخاب‌شده را به Store API بومی وصل می‌کند.
محصول متغیر بدون انتخاب معتبر ذخیره نمی‌شود؛ حذف با پاسخ خالی `204` مدیریت می‌شود.

این ویژگی در نصب فعلی فعال است، ولی وابسته به نسخه و ویژگی بومی Woo است. قالب در هر
درخواست option آن را روشن نمی‌کند. هنگام ارتقای Woo یا انتقال به سایت دیگر، وجود و
فعال‌بودن feature و API بومی را بررسی کن؛ تست عدم دسترسی مشتری دیگر ضروری است.

## ۸. هماهنگی پیشخوان و سفارش‌های پرداخت‌نشده

ایراد: پیشخوان یک سفارش را با عنوان پیش‌نویس می‌شمرد، ولی تاریخچهٔ سفارش‌ها آن را نشان
نمی‌داد و پیام تأیید ایمیل باعث تصور نبود سفارش می‌شد. علت ترکیب فیلتر پیش‌فرض حذف
`checkout-draft` و query متفاوت شمارنده/تاریخچه بود.

`inc/woocommerce/orders.php` اکنون query مشترک را با اولویت ۱۰۰ پس از Woo اعمال می‌کند.
سفارش متعلق به `customer_id` جاری خوانده می‌شود؛ پیش‌نویس دارای کالا و مبلغ قابل پرداخت
دیده می‌شود، پیش‌نویس خالی/صفر نه. صفحه‌بندی پیش‌فرض ۱۰ سفارش و مستقل از تعداد نوشته‌های
بلاگ است. وضعیت نمایشی draft در حساب «در انتظار پرداخت» با نشان زرد است؛ وضعیت واقعی
دیتابیس، موجودی و گزارش مالی تغییر نمی‌کنند. شمارندهٔ منتظر پرداخت نیز اضافه شده است.

پیام بومی اتصال سفارش‌های مهمان به انتهای فهرست منتقل شد. حساب بدون ایمیل پیام نامربوط
نمی‌بیند؛ ایمیل خودکار تأیید نمی‌شود و سفارش مهمان با شباهت ایمیل بی‌اجازه وصل نمی‌شود.
نمایش شمارهٔ سفارش در موبایل، که CSS بومی پنهان می‌کرد، نیز اصلاح شده است.

## ۹. دو درگاه مستقل پرداخت

خواستهٔ کاربر بله‌پی و کارت‌به‌کارت تحت یک پلاگین بود. `voiceweb-payments` مستقل از قالب،
Auth و ACF است؛ HPOS، Checkout Block، checkout کلاسیک و order-pay را پشتیبانی می‌کند.

بله از پرداخت کیف‌پولی بازو و `sendInvoice` استفاده می‌کند. سفارش با لینک خصوصی به بازو
می‌رود؛ pre-checkout فقط اجازهٔ پرداخت است. استعلام `inquireTransaction` پس از پیام موفق
باید مبلغ، شناسه، پرداخت‌کننده و وضعیت را تأیید کند، سپس `payment_complete()` اجرا می‌شود.
قفل هر سفارش و شناسه‌های یکتا از اجرای دوباره جلوگیری می‌کنند. وب‌هوک روی دامنهٔ عمومی
HTTPS ثبت می‌شود؛ `.local` مسیر عملیاتی دریافت وب‌هوک نیست.

کارت‌به‌کارت کارت مقصد و مبلغ snapshotشدهٔ سفارش را نمایش می‌دهد. مشتری تصویر رسید،
شمارهٔ پیگیری و چهار رقم آخر کارت مبدأ می‌فرستد؛ تصویر بازپردازش و رمزگذاری می‌شود.
مدیر در صف خصوصی رسید، بعد از تطبیق با بانک تأیید یا با دلیل رد می‌کند. تا تأیید معتبر،
سفارش پرداخت‌شده نیست. تصویر در Media Library یا لینک عمومی قابل مشاهده قرار نمی‌گیرد.

در بررسی توسعه، اشکال resize تصویر کوچک، تشخیص رسید آخر با شناسهٔ تصادفی، فرم تو‌در‌توی
پنل سفارش، بارگذاری دیرهنگام Blocks، بررسی نتیجهٔ payment_complete و رزرو تکراری موجودی
اصلاح شدند. تست‌ها با پاسخ شبیه‌سازی‌شده‌اند؛ پرداخت عملیاتی بله هنوز آزمایش نشده است.
[چرخهٔ کامل، مدیریت رسید و بازیابی](./PAYMENTS.fa.md)

## ۱۰. فروشگاه با فیلترهای کامل

خواسته: فیلتر بازهٔ قیمت، ارزان‌ترین/گران‌ترین و تجربهٔ موبایل مشابه فروشگاه‌های بزرگ.
پیاده‌سازی بدون پلاگین اضافه در catalog قالب است. گزینه‌ها از دادهٔ واقعی Woo ساخته می‌شوند.

| قابلیت | نتیجه |
|---|---|
| قیمت | ورودی از/تا، دو دستگیره، واحد واقعی Woo و پذیرش رقم فارسی/عربی |
| مرتب‌سازی | پیشنهادی، جدیدترین، پرفروش‌ترین، قیمت صعودی/نزولی و امتیاز |
| کالا | موجود، تخفیف‌دار، امتیاز ۴+ و جست‌وجوی محصول |
| گروه‌ها | دسته، برند بومی و ویژگی عمومی مثل رنگ/حافظه؛ چندانتخابی |
| دسکتاپ | سایدبار با اسکرول داخلی؛ تغییر گزینه پس از ۲۲۰ms اعمال می‌شود |
| موبایل | dialog جدا برای فیلتر و مرتب‌سازی؛ فیلترها موقت تا زدن «نمایش محصولات» |
| ناوبری | URL قابل اشتراک، Back/Forward و صفحه‌بندی؛ هر تغییر فیلتر صفحهٔ اول |
| شبکه | fetch HTML همان archive، لغو درخواست قدیمی و امکان تلاش دوباره در خطا |
| بدون JS | فرم GET و لینک‌ها همچنان قابل استفاده‌اند |

داخل یک گروه OR و بین گروه‌ها AND اعمال می‌شود. برند/ویژگی بدون محصول، دادهٔ نمایشی
ساختگی تولید نمی‌کند. تا ۱۰۰ گزینه در گروه و ۵۰ انتخاب پذیرفته می‌شود. قیمت محصول متغیر
مطابق بازه و lookup بومی Woo است، نه تضمین تطبیق تمام ویژگی‌ها در یک variation منفرد.
سقف کشویی از محصولات عمومی همان archive می‌آید و با فیلتر فعال کوچک نمی‌شود.

آخرین درخواست کاربر جهت دستگیره‌ها بود: در فارسی، **دستگیرهٔ راست «از/حداقل» و چپ
«تا/حداکثر»** است. direction کنترل‌ها از صفحه ارث می‌رسد و نوار رنگی نیز برحسب RTL/LTR
محاسبه می‌شود. drag واقعی مرورگر بررسی کرد که حرکت راست فقط «از» و حرکت چپ فقط «تا»
را تغییر دهد. در LTR جای دو دستگیره مطابق جهت طبیعی صفحه معکوس است.

## شواهد آزمون و حدود تحویل

این موارد در مراحل پیاده‌سازی گفتگو گزارش شده‌اند؛ **در نوبت مستندسازی دوباره اجرا
نشده‌اند**. فرمان‌ها و دامنهٔ هر تست در [RUNBOOK.fa.md](./RUNBOOK.fa.md) آمده است.

- آزمون PHP دفترچه/checkout: ۳۹ بررسی موفق؛ مرورگر مسیرهای حساب، مودال، بلوک و order-pay.
- مرورگر هدر/علاقه‌مندی: صفحه‌کلید، مهمان، variation، حذف ۲۰۴ و مالکیت خصوصی.
- مرورگر سفارش‌ها: شمارنده/تاریخچه، draft قابل پرداخت، حذف draft خالی، مشتری دیگر و موبایل.
- Payments: ۳۹ بررسی integration و مرورگر شامل رسید رمزگذاری‌شده، رد/ارسال مجدد، تأیید مدیر،
  nonce/مالکیت، checkout بلوکی و عرض ۳۲۰؛ شبکهٔ بله و ایمیل‌های تست مسدود بودند.
- کاتالوگ: فیلترهای ترکیبی، ترتیب بومی، قیمت متغیر، تاریخچه، خطای شبکه، حالت بدون JS،
  موبایل و drag واقعی RTL؛ fixtureهای موقت پاک شدند.
- Auth: regression، بوت یک‌خطی، هر دو سرویس شبیه‌سازی‌شده و smoke مرورگر؛ یک آزمون واقعی
  مهر افراز با اجازهٔ کاربر در گذشته، بدون آزمون واقعی کاوه‌نگار.

تصاویر QA و ZIP پرداخت در مراحل قبلی در پوشهٔ موقت ساخته شدند؛ artifact موقت نسخهٔ
مرجع یا تحویل دائمی نیست. سورس مخزن و تست‌های نام‌دار منبع ادامهٔ کار هستند.
درخواست‌های عنوان کامیت در گفتگو پیشنهاد عنوان بوده‌اند؛ این سند ادعا نمی‌کند که
کامیت، push، انتشار فروشگاه یا استقرار عملیاتی توسط دستیار انجام شده است.

## چه چیزهایی هنوز به اقدام نیاز دارد؟

| موضوع | اقدام بعدی |
|---|---|
| بله عملیاتی | توکن معتبر، بازوی اختصاصی، دامنهٔ عمومی HTTPS، آزمایش اتصال/وب‌هوک و آزمون واقعی مجاز |
| کاوه‌نگار عملیاتی | API key، الگوی تأییدشده و آزمون واقعی مجاز؛ فعلاً فقط تست mock |
| WebOTP | HTTPS و مرورگر پشتیبان؛ روی دامنهٔ محلی HTTP نباید تضمین شود |
| کارت‌به‌کارت | روش اکنون فعال است؛ مسئول فروشگاه باید رسیدها را با گردش حساب بانک تطبیق دهد |
| دادهٔ فروشگاه | فعلاً یک محصول منتشرشده؛ برند/ویژگی/محصول کافی برای فیلترهای واقعی اضافه شود |
| انتشار | فروشگاه هنوز «به‌زودی» است؛ این وضعیت با مستندسازی تغییر داده نشده |
| ارتقای Woo | بررسی native wishlist، Blocks، Store API و overrideهای account پیش از انتشار |

| پشتیبان | دیتابیس + فایل‌های رسید + salts وردپرس به‌صورت امن؛ بدون salts رمزگشایی ممکن نیست |
| آرشیو مالی | سیاست نگهداری/حذف رسید با مسئول فروشگاه؛ پاک‌سازی خودکار مالی وجود ندارد |
| بازپرداخت | انتقال واقعی وجه دستی و سپس ثبت در Woo؛ افزونه بازپرداخت بانکی خودکار ندارد |

## به‌روزرسانی همین مستندات

پس از هر تغییر رفتار، سند تخصصی و این تاریخچه را در همان تغییر به‌روز کن. شمارهٔ نسخه و
وضعیت تنظیمات را از نصب مورد بررسی بگیر، نه از گفتهٔ قدیمی گفتگو. در بخش آزمون روشن کن
چه چیزی واقعاً اجرا شده و چه چیزی برنامهٔ بررسی است. اطلاعات محرمانه و محتوای خصوصی
مشتری را در Doc یا خروجی تست قرار نده. برای شروع کار بعدی: این سند، سپس RUNBOOK و راهنمای
بخش موردنظر خوانده شوند.
